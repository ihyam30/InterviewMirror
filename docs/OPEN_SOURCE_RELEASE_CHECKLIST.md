本清单区分“公开源代码仓库”和“将完整应用打包分发或运营为在线服务”。它不是法律意见；第三方组件许可和服务合规范围需结合实际分发及运营方式确认。

## 第三方组件与许可边界

项目许可证只覆盖项目有权许可的部分，不会把第三方依赖、模型权重、运行时、字体或外部服务自动改为 Apache-2.0。它们继续受各自许可证和条款约束。

当前需要重点审查的组件：

| 组件 | 仓库中的用途 | 发布前动作 |
|---|---|---|
| MinIO Server | Compose 中由 `deploy/minio/Dockerfile` 从 MinIO 源码构建，MinIO 上游标示为 AGPL-3.0，且仓库已归档 | 若分发包含该服务的整套镜像/安装包，或将应用作为在线服务运营，先评估具体组合与义务；考虑换成有持续维护、许可适合的对象存储实现。不要据此推断 InterviewMirror 主代码自动变为 AGPL。 |
| MinerU | 本机文档解析 Worker/模型工具 | 核对当前锁定版本的 MinerU 自定义许可证及模型权重条款；若提供在线服务，按该版本许可证核对署名等要求。 |
| Maven / npm / Python 依赖 | 后端、前端、评测脚本 | 发布二进制或容器前，生成完整传递依赖 SBOM 和许可证报告，逐项审查 NOTICE、署名、源码提供及兼容性要求。当前清单尚不是完整传递依赖清单。 |
| 样本、字体和展示图片 | 解析评测、PDF 渲染和 README | 确认其作者、来源、许可和公开权限；Windows 字体文件不得随项目复制或分发，除非其许可明确允许。 |

## 在线服务上线前

当前 Compose 明确用于本机演示，不代表已通过生产部署或法律合规验收。若要让外部用户使用，至少需要：

- 更换/移除演示账号与默认密码；生成独立数据库、对象存储、Session、Worker 和模型密钥，并使用受控密钥管理。
- 将 TLS、可信代理、Cookie Secure、CSRF、上传限制、备份、审计、监控和恢复策略按目标环境重新配置并进行安全测试。
- 发布隐私告知、处理目的/范围/保存期/删除办法、用户授权和第三方模型处理说明；验证模型供应商的数据区域、留存与训练政策。
- 评估目标运营地适用的个人信息、生成式 AI、内容标识、互联网服务备案/许可和投诉处理要求。不要把本地 demo 的配置或合规检查表视为在线服务批准。

## 每次公开发布前的复核

- [ ] 许可证持有人/贡献者授权确认完成；所有项目自有文件的许可范围清晰。
- [ ] 检查 `git status`、所有待发布提交和完整 Git 历史；运行 secret scanning，并处理全部告警。
- [ ] 检查 Git 作者/提交者元数据是否暴露私人邮箱；如需改写历史，先通知协作者、备份 refs、制定回滚方法，再安排 force push 窗口。
- [ ] 检查 tracked assets、样本、日志、评测结果和截图，不包含真实个人信息、密钥、私有材料或未授权作品。
- [ ] 生成并审查完整 SBOM 和传递依赖许可证报告；为实际分发物附带所需许可证及通知。
- [ ] 决定 MinIO 的处理方案；对容器镜像、Compose 和在线服务的分发形式完成许可审查。
- [ ] 检查 MinerU 代码和权重版本许可、字体和模型供应商条款。
- [ ] 若部署在线服务，完成独立的隐私、安全和适用监管要求评估。
